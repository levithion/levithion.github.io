Lumina Local-First Multimodal Memory Search Engine

Jul 2026 — Aug 2026

Lumina indexes your screenshots and photos entirely on-device, captions each one with a local vision-language model, and makes the whole library searchable by meaning, on-screen text, and time. Nothing ever leaves the machine.

3 fused signalsVisual · semantic · exact text
~10 secondsNew screenshot to searchable
Zero cloudLocal models, embedded Qdrant, localhost-only API

Problem and objective

A few months of normal computer use produces thousands of files named “Screenshot 2026-08-12 at 10.34.17.png”. The information needed to find one again — which app it showed, what the error message said, roughly when it happened — exists only inside the pixels. Filename search cannot help, and shipping a personal screen history to a cloud vision API is not an acceptable trade for convenience.

The objective became: type what you remember — “the terminal error about permissions last week”, “that hotel listing with a brick wall” — and get the image back, under a hard constraint that every caption, embedding, and byte of data stays on the machine.

From cloud demo to local-first product

The first version of Lumina looked conventional: it encoded a fixed collection of 8,092 images with CLIP, stored vectors in hosted Qdrant, and served results through FastAPI and Streamlit. Operating that deployment surfaced recurring failures — payloads referencing files missing from the serving container, credentials committed to public source, scheduled sync jobs failing silently for days. Each incident demanded a redesign rather than a patch.

The current Lumina inverts the topology. Instead of moving images toward a cloud index, it moves the index to the images: an embedded Qdrant store, on-device models, and a localhost server wrapped in a native window. Privacy stopped being a promise in a README and became an architectural property.

System architecture

Embedded Qdrant allows exactly one process per data directory, and that constraint shaped everything else. Rather than fight it with locks and IPC, Lumina embraces it: main.py hosts the FastAPI server, both encoder models, the filesystem watcher, and the database in a single OS process. Launching a second instance fails fast with human guidance (lsof qdrant_data/.lock, or point MEMORY_STORAGE_PATH elsewhere) instead of corrupting the store.

  • Ingestion: discovers JPEG, PNG, and HEIC files, extracts EXIF/mtime capture dates, runs SmolVLM captioning plus optional Tesseract OCR, computes dual embeddings, and upserts points in batches of 32.
  • Storage: embedded Qdrant holds two named vector spaces per point — a 512-dimensional CLIP visual vector and a 384-dimensional MiniLM vector over caption + OCR + tags — alongside payload indexes for datetime, keyword, and full-text fields.
  • Retrieval: hybrid search fuses visual similarity, semantic similarity, and exact token overlap, with safety and date-range filters pushed into Qdrant before top-K truncation.
  • Interface: a pywebview native window over static UI assets, served by FastAPI bound to 127.0.0.1:8337. Headless --web mode and a launchd plist run the same engine without a window.

Why three signals beat one

Raw CLIP similarity alone is weak for this domain: screenshots of the same app look nearly identical visually, so a query about a specific error returns every terminal window ever captured. Lumina therefore scores each result from three complementary signals. A MiniLM embedding of the caption-plus-OCR document carries meaning, an exact term-overlap score anchors literal matches (“permissions” must literally appear), and the CLIP visual vector still finds images no text describes well.

The default memory profile weights these at 10% visual, 50% semantic, 40% exact. Candidate generation pulls max(limit × 4, 40) hits from each vector space independently, merges them by point ID, then reranks the union — so a result that only one source discovered can still win after fusion.

Queries that understand time

Memory requests are saturated with temporal language, so the server parses it before embedding anything. A stdlib-only parser recognizes phrases like “yesterday”, “last week”, “in March”, and “since June”, strips them from the query, and resolves them against the current clock into concrete UTC bounds. The remaining text becomes the embedding; the bounds become a DatetimeRange filter on the indexed created_at field.

Evaluating that filter inside Qdrant matters for correctness, not just speed: it constrains the candidate pool before top-K truncation, so a match from six months ago cannot be crowded out by forty fresher near-misses. Only one date phrase per query is interpreted — combining “last week in March” stays deliberately ambiguous instead of silently wrong.

An ingestion pass that respects your time

The first full-library scan is genuinely expensive because SmolVLM captions every new file. Everything after it is engineered to be nearly free. A stat-signature cache (size plus nanosecond mtime) identifies unchanged files without re-hashing or touching the database. Files that did change are hashed once with SHA-256; that digest becomes the point’s deterministic UUID, which makes identity content-addressed rather than path-based.

That choice pays off repeatedly. A file moved to a new folder is repaired in place with a payload update instead of being re-captioned. An edited screenshot indexes as its own new point while an hourly-throttled sweep deletes the superseded one. Failed files keep their failure status and retry automatically on the next scan, so transient errors never strand items permanently.

Live indexing

A watchdog observer over macOS FSEvents feeds a trailing-edge debouncer: saving one screenshot fires a burst of events, but the scan triggers exactly once, ten seconds after activity settles. Because scan_library is idempotent, timer-thread re-entry is safe, and a failed watch cycle logs a warning and waits for the next change rather than killing the thread. New screenshots become searchable roughly ten seconds after capture, with no manual action.

Reverse image search and duplicate detection

Any image can be posted to the API as a probe. Lumina embeds it with CLIP for neighbor search and hashes it with a perceptual hash for copy detection; Hamming distance zero marks an exact repost and distance up to eight marks a near-duplicate. Duplicate tiers are promoted above plain visual neighbors during ranking, so when you ask “where did I see this?”, the original outranks everything similar to it.

Loud failure beats silent success

Silent degradation was the recurring enemy across versions: captioning failures produced empty captions nobody noticed, sync jobs skipped uploads without error, and an unreachable database was indistinguishable from a missing collection. Every one of those paths now fails loudly — a disabled captioner prints why, storage conflicts exit with instructions, and health status exposes counts, watcher state, and last-scan failures.

Privacy and security posture

The privacy model is enforced by construction. Embeddings, captions, and OCR run locally; the server binds to loopback only; and uninstalling means deleting the project folder. File-serving endpoints verify that a requested absolute path actually exists in the index before touching the filesystem, returning 404 otherwise — nothing outside the library is reachable through the API. The SmolVLM safe-content verdict is stored as an is_sensitive payload field and enforced as a database-level must_not filter, which also keeps legacy points lacking that field visible rather than silently hidden.

Testing and CI

The app factory accepts injected encoder and client objects, so the test suite stubs the model layer entirely. CI installs only lightweight dependencies — no multi-gigabyte torch download — and covers ingestion cache behavior, dedup and move repair, sweep correctness, hybrid ranking math, date-phrase parsing, and every API endpoint including the indexed-path security checks.

Trade-offs and limitations

The design is macOS-first: Finder reveal via open -R and the launchd integration assume a Mac, though the retrieval engine itself is portable Python. First-run indexing is slow while SmolVLM captions the backlog; CAPTION_ENABLED=0 trades caption recall for a fast OCR-and-visual-only pass. Tesseract remains optional, but its absence measurably hurts recall on text-heavy screenshots. Finally, the safe-content filter is a small-model heuristic — helpful, not a guarantee.

Outcome and next steps

Lumina now closes the loop it originally proved — encode, store, search, serve — but on terms a personal archive actually requires: incremental freshness, honest failure modes, and privacy by architecture. Planned next steps include a relevance-judged evaluation set for tuning fusion weights, latency percentile tracking behind the status endpoint, quantized ONNX encoders for faster cold starts, and portable replacements for the macOS-specific reveal and autostart layers.
